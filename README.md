# Teams Meeting Insights MCP Server

An MCP server that syncs Microsoft Teams meeting data (transcripts, AI insights, action items) into Elasticsearch so Claude can search your meeting history.

Runs as two Docker containers — Elasticsearch and a Node.js server — with a web dashboard for Microsoft sign-in.

## Quick Install

```bash
curl -fsSL https://raw.githubusercontent.com/WayneJetski/teams-meetings-mcp/main/scripts/install.sh | bash
```

This clones the repo, prompts for your Azure credentials, starts the containers, and adds `teams-mcp` to your PATH.

Options:

```bash
# Install to a specific directory
curl -fsSL ... | bash -s -- --dir ~/tools/teams-mcp

# Use HTTPS instead of SSH for git clone
curl -fsSL ... | bash -s -- --https
```

Once installed, manage the server with:

```
teams-mcp              # Start the server (default)
teams-mcp stop         # Stop containers
teams-mcp logs         # Tail container logs
teams-mcp update       # Pull latest + rebuild
teams-mcp update --force  # Rebuild + restart even if already up to date
teams-mcp status       # Container & health status
teams-mcp uninstall    # Remove teams-mcp completely
teams-mcp help         # Show all commands
```

## Manual Setup

### Prerequisites

- Docker and Docker Compose
- Node.js 20+
- An Azure AD app registration (see [Azure Setup](#azure-ad-setup) below)

### 1. Clone and start

```bash
git clone https://github.com/WayneJetski/teams-meetings-mcp.git
cd teams-meetings-mcp
./scripts/start.sh
```

On first run, the script will create `.env` from the template and ask you to fill in your Azure credentials:

```bash
AZURE_TENANT_ID=your-tenant-id
AZURE_CLIENT_ID=your-client-id
AZURE_CLIENT_SECRET=your-client-secret
```

Once those are set, run `./scripts/start.sh` again. It will build and start the Docker containers and register the MCP server with Claude Code.

### 2. Sign in

Open http://localhost:4005 and sign in with your Microsoft account. Your first sync runs automatically after sign-in.

### 3. Use with Claude

The start script auto-configures the MCP server in Claude Code. Restart Claude Code to pick it up. Claude will then have access to these tools:

| Tool | Description |
|---|---|
| `search_meetings` | Full-text search across summaries, transcripts, action items, decisions |
| `get_meeting` | Full details of a specific meeting by ID |
| `get_action_items` | Action items, filterable by owner and date range |
| `get_decisions` | Decisions, filterable by keyword and date range |
| `meeting_stats` | Aggregated stats: meeting count, top attendees, topics |

## Azure AD Setup

### 1. Register an app

1. Go to **Azure Portal** > **Entra ID** > **App registrations** > **New registration**
2. Name: `Teams Meeting Insights MCP` (or whatever you like)
3. Supported account types: **Single tenant**
4. Redirect URI: **Web** — `http://localhost:4005/auth/callback`

### 2. Add API permissions

Go to **API permissions** > **Add a permission** > **Microsoft Graph**:

**Delegated permissions:**

| Permission | Purpose |
|---|---|
| `OnlineMeetings.Read` | List the signed-in user's meetings |
| `OnlineMeetingTranscript.Read.All` | Read meeting transcripts |
| `Calendars.Read` | Discover meetings via calendar |
| `User.Read` | Read signed-in user profile |
| `OnlineMeetingAiInsight.Read.All` | AI insights (requires Copilot license) |

Click **Grant admin consent** for your org.

### 3. Create a client secret

Go to **Certificates & secrets** > **New client secret** > copy the value into your `.env`.

## Data Tiers

Set `GRAPH_DATA_TIER` in `.env` to control what gets synced:

| Value | License Required | What it pulls |
|---|---|---|
| `transcripts` (default) | M365 E3/E5/Business | Raw `.vtt` transcripts |
| `insights` | M365 Copilot | Structured AI insights (notes, action items, decisions) |
| `both` | M365 Copilot | Both — AI insights as primary, transcripts for deep search |

## Environment Variables

| Variable | Required | Default | Description |
|---|---|---|---|
| `AZURE_TENANT_ID` | Yes | — | Azure AD tenant ID |
| `AZURE_CLIENT_ID` | Yes | — | Azure AD app client ID |
| `AZURE_CLIENT_SECRET` | Yes | — | Azure AD client secret |
| `SESSION_SECRET` | Auto | — | Auto-generated by start script |
| `ES_SECRET` | Auto | — | Elasticsearch `elastic` password; auto-generated by the install/start/update scripts |
| `GRAPH_DATA_TIER` | No | `transcripts` | `transcripts`, `insights`, or `both` |
| `SYNC_CRON` | No | `0 * * * *` | Cron schedule for auto-sync (default: hourly) |
| `SYNC_LOOKBACK_DAYS` | No | `30` | Maximum window a sync will look back over |
| `ES_MAX_RETRIES` | No | `5` | Elasticsearch client retry attempts per request |
| `ES_REQUEST_TIMEOUT_MS` | No | `30000` | Elasticsearch client per-request timeout (ms) |

### How the sync window moves

Each run records a watermark and the next run reaches back to it (plus a one-day
overlap buffer), capped at `SYNC_LOOKBACK_DAYS`. Steady state is therefore a
cheap two-day window.

The watermark only advances past occurrences that were actually captured. If an
occurrence can't be indexed (transcript not published yet, a Graph error), the
watermark is held at it and the next run retries, so a gap heals itself once the
underlying problem clears. Runs that end this way log at `warn` with
`uncaptured` and `oldestUncapturedStart`.

An occurrence that will never have a transcript can't pin the window open
forever: the hold is floored at `SYNC_LOOKBACK_DAYS`. To recover data older than
that, force a full sync, which ignores the watermark entirely:

```bash
curl -X POST http://localhost:4005/sync \
  -H 'Content-Type: application/json' -d '{"lookback_days": 30}'
```

## Security

Meeting data (transcripts, AI insights, action items) is sensitive, so
Elasticsearch is locked down:

- **Authentication required.** Elasticsearch runs with security enabled. The web
  app authenticates as the built-in `elastic` user using `ES_SECRET`, a random
  value auto-generated into `.env` on install and backfilled on update. It is
  never committed (`.env` is gitignored).
- **Not exposed on the host.** Elasticsearch has no host port mapping — it only
  listens inside the internal Docker network, reachable by the MCP server at
  `elasticsearch:9200`. Nothing on your machine can reach it directly.

### Direct access (when you need it)

Because the port isn't published, use the on-demand tunnel to talk to
Elasticsearch directly (for debugging or one-off queries):

```bash
./scripts/es-tunnel.sh            # forwards 127.0.0.1:9200 -> elasticsearch:9200
./scripts/es-tunnel.sh 9250       # use a different local port
```

It prints an authenticated `curl` example and closes when you press Ctrl-C.

## Troubleshooting

**`cluster_block_exception` / "disk usage exceeded flood-stage watermark" on the `meetings` index, but disk looks fine:**

Elasticsearch sets a `read_only_allow_delete` block on an index when it believes disk usage crossed the flood-stage watermark (95% by default). If `docker exec meetings-es df -h /usr/share/elasticsearch/data` shows plenty of free space, the block can be stale: ES's own cluster task queue got wedged, so the disk-threshold monitor never got to re-check and lift it. Confirm via the tunnel:

```bash
./scripts/es-tunnel.sh
curl -u elastic:$ES_SECRET http://127.0.0.1:9200/_cluster/pending_tasks
```

A `cluster_reroute(disk threshold monitor)` task stuck in the queue for an unreasonable amount of time is the tell. Fix:

```bash
docker restart meetings-es   # clears the wedged task queue and forces a fresh disk check
curl -X PUT -u elastic:$ES_SECRET http://127.0.0.1:9200/meetings/_settings \
  -H 'Content-Type: application/json' \
  -d '{"index.blocks.read_only_allow_delete": null}'
```

## Tests & CI

Run the suite locally:

```bash
npm test          # node --test, no Docker or credentials needed
```

`test/routes.test.js` boots the app on an ephemeral port and asserts what an
unauthenticated caller can reach: `/health`, `/mcp` and the OAuth discovery
endpoints stay public, and every API route, the dashboard and unknown paths do
not. It needs no Elasticsearch — `/health` is asserted only to be ungated, not
to be green.

### Integration tests

`test/integration/` runs against a real Elasticsearch, because mappings, nested
queries and aggregations cannot be verified any other way — a query naming a
nested field returns zero hits rather than an error. The suite **skips itself**
when no node is configured, so `npm test` stays offline by default.

To run them locally, start a throwaway node and point the suite at it:

```bash
docker run -d --rm --name es-itest -p 19200:9200 \
  -e discovery.type=single-node \
  -e xpack.security.enabled=true \
  -e xpack.security.http.ssl.enabled=false \
  -e ELASTIC_PASSWORD=itest-secret \
  docker.elastic.co/elasticsearch/elasticsearch:8.13.0

ELASTICSEARCH_URL=http://localhost:19200 ELASTICSEARCH_PASSWORD=itest-secret \
  npm run test:integration

docker stop es-itest
```

Each run creates its own `meetings-itest-*` index and deletes it afterwards, so
it never touches a real one.

Every push to `main` and every pull request targeting it runs the unit suite on
Node 20 and 22 via `.github/workflows/ci.yml`, then the integration suite against
an Elasticsearch service container. To gate merges on it, add a branch
protection rule for `main` requiring the `Tests (Node 20)` and `Tests (Node 22)`
status checks to pass.
